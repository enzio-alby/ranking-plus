### Arquitetura

```
Browser → fetch() → Node.js/Express :4000 (api2.js)
                         ├── Pool MySQL (10 conexões) → localhost:3306
                         ├── Nodemailer → Gmail SMTP
                         └── Multer + pdf-parse → buffer RAM
```

## Problemas Que Precisam Ser Corrigidos

> Estes são os pontos que a banca pode questionar diretamente

| Problema | Impacto |
|---|---|
| Senhas armazenadas em plain text no banco | Crítico — segurança básica |
| Dados de alunos hardcoded no areaprofessor.js | Aparece no inspect do browser |
| Sem rate limiting no login | Brute force trivial |
| Sem validação de entrada (email, CPF, CNPJ) | Dados corrompidos no banco |
| Parser PDF do LinkedIn frágil (regex manual) | Pode falhar na demo ao vivo |
| Sem paginação no ranking | Trava se tiver muitos alunos |

## Melhorias Planejadas

### Camada 1 — Obrigatório (corrigir antes de apresentar)

#### 1. bcrypt nas senhas
- [ ] `npm install bcrypt`
- [ ] Trocar INSERT direto por `bcrypt.hash(senha, 10)` no cadastro
- [ ] Trocar SELECT + comparação direta por `bcrypt.compare()` no login
- [ ] Tabelas afetadas: alunos, professores, administradores, empresas
- **Esforço:** ~2h | **Impacto:** elimina o maior gap de segurança do projeto

#### 2. Remover dados hardcoded do areaprofessor.js
- [ ] Localizar array de alunos fictícios no JS do frontend
- [ ] Substituir por chamada à rota `/professores/:id/alunos` (já existe na API)
- **Esforço:** ~30min | **Impacto:** evita exposição de dados fictícios no DevTools

#### 3. Rate limiting no login
- [ ] `npm install express-rate-limit`
- [ ] Aplicar middleware: 5 tentativas por IP a cada 15 minutos
- [ ] Retornar mensagem clara ao usuário quando bloqueado
- **Esforço:** ~30min | **Impacto:** demonstra que você pensou em segurança
